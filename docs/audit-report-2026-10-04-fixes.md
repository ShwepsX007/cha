# Аудит и исправления проекта Chata

**Дата:** 4 октября 2026 г.
**Ветка:** `arena/01a108a1-cha` (от `arena/01a10708-cha`, коммит `6da0eb7`)
**Проверялось:** production-сборка Next.js 16.3.8, живой сервер `next start`,
PostgreSQL-совместимая БД, сквозные API-тесты, обрыв БД, сценарий «пустая БД».

## Краткий вывод

Код приложения в целом рабочий: авторизация, общий чат, сообщения, статусы
прочтения, вложения, профиль, админ-панель и аудит — всё проверено сквозными
тестами. Причина того, что «сервер стартует, а приложение не работает», — не в
бизнес-логике, а в отсутствующих эксплуатационных частях: в репозитории не было
базовой миграции БД, не было ни README со сборкой/деплоем, ни pm2-конфига, а
загрузка аватарок в `public/` в production-режиме Next.js не работает.

Все найденные проблемы исправлены в этой ветке; три из них воспроизведены и
проверены после фикса.

## Почему не запускалось

### 1. В репозитории нет базовой схемы БД (главная причина)

`drizzle/` содержал только инкрементальные миграции `0001`–`0007`, которые
меняют уже существующие таблицы. Ни `0000`, ни `CREATE TABLE users/chats/
chat_members/messages` в репозитории не было, а `drizzle-kit migrate` ничего не
применяет, потому что нет `drizzle/meta/_journal.json` (проверено: таблица
`__drizzle_migrations` не создаётся, миграции не выполняются).

Единственным способом создать схему был ручной `drizzle-kit push` (dev-зависимость),
нигде не задокументированный. Если его не выполнить, получается то, что видно в
`pm2 logs chata`: сервер пишет `✓ Ready`, а в браузере — бесконечная загрузка и
«Ошибка сервера». Воспроизведено на чистой БД:

```
GET /api/health  → {"ok":false,"schema":"missing","missingTables":[...],"hint":"Run: npm run db:setup"}
GET /api/chats   → {"error":"Server error"}
POST /api/auth/login → {"error":"Ошибка сервера"}
```

**Исправлено:** добавлена идемпотентная базовая миграция `drizzle/0000_init.sql`
(схема побайтово совпадает с `src/db/schema.ts` — проверено `drizzle-kit push:
No changes detected` после её применения) и скрипт `npm run db:setup`, который
применяет все `drizzle/*.sql` по порядку. Скрипт написан на чистом Node ESM и
работает при `npm ci --omit=dev`, без `tsx`/`drizzle-kit`.

### 2. Загруженные аватарки не отдавались браузеру

`POST /api/profile/avatar` сохранял файл в `public/avatars/` и возвращал
`/avatars/<файл>.webp`. В production-режиме Next.js 16 фиксирует содержимое
`public/` в момент старта процесса, поэтому файл, созданный во время работы,
отдаётся как **404** до перезапуска pm2. Воспроизведено:

```
upload → 200 {"avatarUrl":"/avatars/ab5119b8....webp"}
GET /avatars/ab5119b8....webp → 404   (до перезапуска)
GET /avatars/ab5119b8....webp → 200   (после перезапуска сервера)
```

**Исправлено:** файлы теперь хранятся вне `public/` (`UPLOAD_DIR`, по умолчанию
`./.data/avatars`) и отдаются маршрутом `src/app/avatars/[fileName]/route.ts`
с проверкой имени файла. Старые файлы из `public/avatars/` продолжают
отдаваться тем же маршрутом, так что существующие профили не ломаются.

### 3. Нет `.env` / нет production-сборки

Без `DATABASE_URL` приложение падает при импорте модуля БД, без `JWT_SECRET` —
при первом запросе к API авторизации в production. `next start` без
предварительного `npm run build` работать не может, а перезапуск pm2 после
`git pull` без пересборки оставляет старую сборку.

**Исправлено:** `README.md` с полным порядком действий, `ecosystem.config.cjs`
для pm2, `scripts/deploy.sh` (`npm run deploy`) — зависимости → миграции →
сборка → reload pm2 → health check.

### 4. Диагностика была недоступна

`/api/health` отвечал `{"ok":true}` независимо от состояния схемы.

**Исправлено:** health-check теперь сообщает `database`, `schema`
(+ `missingTables` и подсказку), `matrix` и наличие конфигурации `jwtSecret/
matrix/telegram/push`, не раскрывая секретов.

## Прочие найденные и исправленные ошибки

| # | Проблема | Исправление |
|---|---|---|
| 1 | Пул PostgreSQL создавался без обработчика `error`: обрыв idle-соединения (рестарт СУБД, сетевой сбой) выбрасывает необработанное событие и **убивает процесс** — «приложение само упало» | `src/db/index.ts`: `pool.on("error")`, лимиты `max`/`idleTimeoutMillis`/`connectionTimeoutMillis`, кэш пула на `globalThis` во всех окружениях |
| 2 | После «nuclear wipe»/удаления чата пользователь навсегда оставался без «Общего чата»: членство добавлялось только при регистрации | `src/lib/chats.ts::ensureGeneralChatMembership`, вызывается из регистрации и `/api/chats`; проверено: после удаления чата он создаётся заново, дубликатов нет |
| 3 | Регистрация проверяла членство в общем чате неправильно (любой член, а не текущий пользователь) → возможны дубли строк в `chat_members` | Исправлено + миграция `0008_integrity.sql` (дедупликация и уникальный индекс `(chat_id, user_id)`) |
| 4 | Имя `telegram_admin` можно было занять самостоятельной регистрацией до запуска бота | Логин зарезервирован (409) |
| 5 | `/api/auth/me` возвращал 401 при любой ошибке, включая недоступность БД: авария СУБД выглядела как «разлогинило всех» | Инфраструктурные ошибки логируются и возвращают 500; проверено поведение при остановке и перезапуске БД (восстановление без перезапуска приложения) |
| 6 | Мёртвый код: `saveLocalBuffer`/`removeLocalFile` в `src/lib/telegram.ts` после перехода на `src/lib/storage.ts` | Удалено |
| 7 | Аватарки и прочие runtime-файлы могли попасть в git | `.gitignore`: `.data/`, `logs/`, `public/avatars/*` (кроме `.gitkeep`) |

## Что проверено и работает

Проверено на живом сервере (production-сборка, `next start`):

- `/api/health` — `{"ok":true,"database":"ok","schema":"ok","matrix":"not_configured"}`;
- развёртывание на **чистой** БД только командой `npm run db:setup` (без `drizzle-kit push`);
- регистрация, вход, `/api/auth/me`, автоматическое вступление в «Общий чат»;
- отправка и чтение сообщений, статусы `sent → delivered → read`, `/api/messages/[chatId]/receipts`;
- загрузка аватарки и **немедленная** отдача файла (регрессионный тест пройден), удаление аватарки;
- профиль: смена отображаемого имени, смена пароля;
- админ-панель: пользователи, поиск, бан/разбан (бан реально блокирует отправку), роли, журнал аудита, модерация, `/admin`;
- восстановление членства в общем чате и отсутствие дубликатов;
- поведение при недоступной БД: `/api/health` → 500 с причиной, `/api/auth/me` → 500, процесс не падает, после возврата БД всё восстанавливается без перезапуска;
- `npm run typecheck`, `npm run lint`, `npm run build`, `npm run db:check`, `npm run smoke` — успешно.

## Как теперь запускать

```bash
cp .env.example .env      # DATABASE_URL и JWT_SECRET обязательны
npm ci
npm run db:setup
npm run build
npx pm2 start ecosystem.config.cjs     # или bash scripts/deploy.sh
curl -s http://127.0.0.1:8010/api/health
```

Проверка запущенного сервера: `npm run smoke` (только чтение) или
`SMOKE_ALLOW_WRITES=1 npm run smoke` (создаёт два временных аккаунта и
проверяет сообщения, статусы и аватарку).

## Остаётся за пределами репозитория

Эти пункты нельзя проверить без вашего сервера и внешних сервисов:

- **Matrix/Synapse**: `MATRIX_*` должны быть заданы все четыре одновременно; без
  них приватные чаты недоступны, а старые помечены `legacy`. Сквозной сценарий
  E2EE (создание комнаты, QR-верификация, восстановление ключей) в этом аудите
  не проверялся — для него нужны два устройства и живой homeserver.
- **Telegram**: без `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` загрузка файлов в
  общий чат возвращает сообщение о ненастроенном хранилище.
- **Web Push**: без VAPID-ключей эндпоинт отдаёт `configured:false`, интерфейс
  показывает понятную ошибку.
- **Инфраструктура**: права на запись в `UPLOAD_DIR`, nginx-прокси, бэкапы БД.

## Рекомендации (не являются ошибками)

1. **Первый зарегистрированный пользователь становится администратором.** Для
   публичного сайта это риск: первый посетитель получит админку. Безопаснее
   задать `INITIAL_ADMIN_IDENTIFIER` (или создать админа ботом) и закрыть
   регистрацию. Поведение оставлено прежним, чтобы не менять ваш сценарий
   развёртывания.
2. `/api/chats` делает несколько запросов на каждый чат (N+1) и опрашивается
   каждые 3 секунды; при росте числа чатов это стоит оптимизировать одним
   запросом с агрегацией.
3. `matrix-js-sdk` импортируется в основной бандл страницы (`src/components/
   ChatApp.tsx`). Работает, но увеличивает первую загрузку; перечисление
   `ClientEvent/SyncState` можно вынести в динамический импорт.
4. Полный `npm audit` показывает предупреждения в dev-инструментах (ESLint/Next,
   Drizzle Kit/esbuild); production-зависимости чистых (`npm audit --omit=dev` —
   0). Принудительный downgrade не применялся.
