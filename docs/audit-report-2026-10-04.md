# Отчёт аудита проекта Chata

**Дата:** 4 октября 2026 г.  
**Ветка:** `arena/01a1035b-cha`  
**Коммит с исправлениями:** `2030bfa` (`Fix Matrix recovery diagnostics and file downloads`)

## Краткий вывод

Проведён целевой статический аудит приложения и сценария «Matrix недоступен, нельзя отправлять сообщения». Одну причину сбоя подтвердить по одному репозиторию нельзя: нет доступа к пользовательской вкладке и серверным переменным окружения production. Найдены и исправлены ошибки восстановления/отображения Matrix-сессии; добавлена безопасная серверная проверка связи с Matrix.

Также обнаружен риск выполнения пользовательского активного файла на домене чата при скачивании. Он устранён: публичные вложения теперь скачиваются как непрозрачные байты, а не открываются браузером как HTML/SVG.

Изменения не ослабляют шифрование, не делают личные комнаты публичными и не меняют правила передачи E2EE-файлов в Telegram.

## Проверенные области

- Восстановление входа приложения и Matrix-сессии в `sessionStorage`.
- Инициализация и синхронизация Matrix-клиента.
- Отображение статуса подключения и блокировка отправки в E2EE-чатах при отсутствии Matrix-сессии.
- Авторизация доступа к чатам и файлам, режимы `public`, `legacy`, `e2ee`.
- Потоки загрузки и скачивания файлов, включая Telegram.
- Production-сборка и аудит зависимостей.

Это ревью кода, а не внешний penetration test и не независимая проверка криптографической реализации.

## Находки и исправления

### 1. Matrix-сессия могла отсутствовать при действующем входе приложения

**Причина:** cookie приложения переживает открытие новой вкладки, а Matrix access token хранится в `sessionStorage` конкретной вкладки. В результате пользователь может быть авторизован в приложении, но не иметь Matrix-сессии в этой вкладке. В прежней логике сохранённый статус `ready` мог дополнительно показывать Matrix как подключённый без действительной сессии.

**Исправлено:** приложение больше не считает Matrix подключённым без Matrix-сессии. Интерфейс показывает, что сессия отсутствует, и подсказывает выйти и войти снова. При этом обычный выход/повторный вход не требует очищать данные сайта. Ошибка Matrix-синхронизации теперь оставляет диагностическую запись в консоли браузера.

**Ограничение:** это правдоподобный сценарий, соответствующий архитектуре хранения сессии, но он не доказывает, что именно он вызвал текущий production-сбой.

### 2. В health-check не было проверки Matrix из процесса приложения

**Исправлено:** `/api/health` после деплоя проверяет базу данных и доступность Matrix Client API по настроенному внутреннему адресу. Проверка ограничена тремя секундами и возвращает только статус, без URL или токенов:

- `matrix: "ok"` — внутренний Matrix Client API доступен приложению;
- `matrix: "not_configured"` — Matrix не настроен;
- `matrix: "unavailable"` — конфигурация неполная или внутренний API не отвечает.

Этот health-check проверяет доступность Client API, но не валидность каждого пользовательского токена и не готовность конкретного E2EE-устройства.

### 3. Скачивание обычных файлов могло открыть активное содержимое на домене чата

**Причина:** endpoint выдавал пользовательский файл как `inline` с пользовательскими MIME-типом и именем файла. Для HTML/SVG это создавало риск выполнения активного содержимого в origin приложения.

**Исправлено:** файлы теперь выдаются как `application/octet-stream` с `Content-Disposition: attachment`, безопасным кодированием имени, `nosniff`, `private, no-store` и sandbox CSP. Доступ по-прежнему требует авторизации и членства в чате.

### 4. Найдены уязвимости зависимостей

После совместимого обновления lock-файла `npm audit --omit=dev` сообщает **0 уязвимостей production-зависимостей**.

Полный `npm audit` всё ещё сообщает **9 проблем только в инструментах разработки**: 5 high и 4 moderate, связанных с цепочками ESLint/Next и Drizzle Kit/esbuild. Предложенные npm принудительные исправления откатывают используемые инструменты на несовместимые старые версии (`eslint-config-next` 14.2.35 и `drizzle-kit` 0.18.1). Такой downgrade не применялся. Эти оставшиеся предупреждения требуют отдельного согласованного обновления dev-инструментов.

## Ограничения, которые сохранены

- Общий чат остаётся открытым и без E2EE.
- Личные и приватные групповые чаты остаются E2EE; при отсутствии Matrix-сессии сообщение не отправляется открытым текстом.
- Существующая plaintext-история остаётся legacy и не объявляется зашифрованной задним числом.
- В E2EE-потоке Telegram получает только ciphertext; исправление скачивания обычных файлов этот поток не меняет.
- Доступ к приватным чатам не расширялся.

## Проверка опубликованного сервиса на момент аудита

До деплоя коммита `2030bfa` внешняя проверка показала:

- `https://chatan.fun/api/health` отвечал `{"ok":true}` — доступна проверка приложения/БД в старой опубликованной версии;
- `https://chatan.fun/_matrix/client/versions` отвечал версиями Matrix Client API — публичный Matrix endpoint был доступен.

Это не проверяет, может ли production-процесс приложения обратиться к внутреннему `MATRIX_INTERNAL_URL`, и не проверяет Matrix-сессию пользователя. Новый ответ `/api/health` появится только после деплоя изменений.

## Рекомендуемые следующие шаги

1. Развернуть коммит `2030bfa`.
2. Открыть `https://chatan.fun/api/health` и посмотреть поле `matrix`.
3. Если интерфейс показывает отсутствие Matrix-сессии — выйти и войти снова в той же вкладке; не очищать данные сайта.
4. Если `matrix` равен `ok`, но синхронизация всё ещё падает, проверить консоль браузера и серверные логи. Не отправлять в отчётах пароли, access token, ключи Matrix или содержимое `.env`.
